# redis-uya v0.9.3 performance analysis

Generated: 2026-07-24 09:21:42 +0800

## Scope

- Host: Intel Xeon E5-2698 v4, 4 visible CPUs, Linux x86_64.
- Workload: single connection, pipeline 1, AOF enabled without explicit fsync.
- Redis baseline: same host, `appendonly yes`, `appendfsync no`, `save ""`.
- redis-uya release command: `make build-release`, using Uya `-O1` and host C `-O3 -DNDEBUG -fno-builtin -fomit-frame-pointer`.
- The benchmark contract records `debug` or `release` from `build/redis-uya.build-mode`, and `make benchmark-v0.9.3-release` rebuilds before measuring.

## Confirmed Root Causes

The replication backlog previously called `sds_range()` every time its logical size exceeded the 1MiB limit. After the buffer became full, every write allocated and copied almost the complete backlog. A 1KiB `SET` therefore introduced roughly 1MiB of extra copying per request during the steady state.

The optimized backlog keeps a logical start offset, advances it in O(1) when old bytes expire, and compacts only after the discarded prefix reaches a threshold. `histlen`, first offset and PSYNC slice semantics remain unchanged.

The next CPU profile found that the default ACL path performed a linear lookup through the generated command catalog on every command even when no category deny rule existed. The shared request gate then repeated the same command, key and channel checks inside the standard executor. For `PING`, generated catalog dispatch and lookup accounted for roughly one quarter of sampled CPU time.

The optimized ACL path maintains an active denied-category count for the default and named users, skips catalog lookup when the count is zero, and performs command/key/channel authorization once in the shared request gate. Category deny semantics remain covered by unit, redis-py and redis-cli tests. A follow-up profile no longer shows command catalog functions above the 0.5% reporting threshold.

The sustained 1KiB `SET` profile then showed `find_chunk` at 88.67% of sampled CPU. Of that, 81.81% came from `resp_alloc_elements()` because every input larger than 64 bytes allocated top-level arrays for the full 64-frame batch limit, even when the buffer contained only one command. The connection path subsequently discarded that one-frame batch and parsed the command again.

The optimized RESP batch parser starts with capacity four and doubles only when additional complete top-level frames are present. Single large commands now stay in allocator slab classes, while real pipelines retain one-pass batch parsing up to the configured limit. A follow-up 20,000-request profile no longer shows `resp_alloc_elements()` above the 0.5% reporting threshold; profiled throughput rose from about 1188 to 3157 req/s.

That follow-up profile exposed a second independent allocation bug: successful standard commands always built a fully quoted MONITOR line before scanning the monitor fd table. With no monitor subscribers, 1KiB `SET` still spent about 53% of sampled CPU growing and copying a line that was immediately discarded.

The monitor registry now maintains an active subscriber count across registration, `RESET`, connection close, transaction cleanup and failed sends. Broadcast returns before allocating an SDS when the count is zero. Real cross-connection monitoring behavior remains unchanged. The next 20,000-request profile reaches 10993 req/s under `perf`, and monitor line construction no longer appears above the 0.5% threshold.

The next event-loop profile showed `server_run_blocked_clients_at()` consuming about 1.9% of samples while no blocking command was pending. The server scanned all 64 client slots on every loop iteration even though the common benchmark never enters a blocking state.

The server now counts clients only after their blocked request has been stored, decrements on successful rescheduling, `CLIENT UNBLOCK` and connection close, and skips the scan while the count is zero. Blocking list/zset wakeup, timeout and explicit-unblock tests remain green. A follow-up 20,000-request profile reaches 12278 req/s and no longer reports the blocked-client scan; the next idle full-table cost is `server_run_buffered_clients_at()` at about 2.2%.

The buffered-client pass had the same common-case problem: after a request was fully consumed, the main loop still scanned all 64 client slots to discover that every `input_len` was zero. The server now tracks clients that actually retain input bytes. Network reads add a client only on the zero-to-nonzero transition; full consumption, close, blocking reschedule and request prepending keep the count synchronized. A zero count skips the scan without changing half-packet, pipeline, pause or blocking semantics.

The matching 20,000-request `SET 1KiB` profile reaches 11751 req/s under `perf`; `server_run_buffered_clients_at()` falls below the 0.5% reporting threshold with no lost samples. The highest user-space symbols are now backlog SDS growth through `find_chunk` at 5.32%, pointer ownership checks at 3.93%, and repeated `default_config` construction at 3.25%.

`CommandReply.config_after` is meaningful only when `request_config_set` is true, but every ordinary reply previously called `default_config()` to populate that inactive field. The same unnecessary full configuration construction existed in zero-copy and batch `ConnectionProcessResult` placeholders. These inactive fields now use zero initialization; successful `CONFIG SET` still copies `runtime.config`, applies updates, sets the request flag and returns the full new configuration.

The follow-up profile reaches 11130 req/s under `perf`. `config_default_config` and its `copy_literal` helper disappear below 0.5%; `command_executor_reply` itself is 1.02%. The release matrix guard passes on the first run, with both SET cases above the per-case Redis superiority throughput threshold and lower p99.

That profile then showed `_pthread_registry_find` at 2.24% in the Future boxing allocator lookup. Uya's interface Future conversion boxes the small read/write future through `async_box_alloc_current`; redis-uya already owns a single-thread `AsyncFramePool`, but every box still queried pthread TSD to recover it.

`std.async` now exposes an explicit single-thread allocator binding. The default setter retains pthread TSD and disables the fast mode, while the server loop opts into a direct process-local allocator pointer under its existing single-thread invariant. The 20,000-request follow-up reaches 10959 req/s under `perf`; `_pthread_registry_find`, `pthread_getspecific` and `std_get_async_frame_allocator` all fall below 0.5% with no lost samples.

The server still read the millisecond clock independently for pause checks, command execution, pause deadlines and client interaction timestamps within one epoll dispatch. Those values describe the same event batch, while cron maintenance and epoll timeout calculation need explicit refresh boundaries.

`RedisServer.event_time_ms` now caches the active event-batch timestamp. The loop refreshes it for maintenance, after maintenance before deriving the epoll timeout, and after epoll returns; command execution, `CLIENT PAUSE`, accept and read interaction updates reuse the cached value. Full pause, idle-client, blocking, slow-reader and persistence integration coverage remains green. In matched 20,000-request profiles, clock-stack samples fall from 40/707 (5.66%) to 32/667 (4.80%), while `SET 1KiB` rises from 10959 to 11287 req/s. Clock work remains visible because the loop deliberately preserves independent maintenance, timeout and post-wait refresh points.

The next write profile showed that a 1KiB string value creates a 1025-byte SDS payload: 1024 data bytes plus the terminating zero byte. That payload missed the existing 1024-byte slab class, so every new value entered the underlying allocator. In the event-time baseline, backlog growth and per-value allocation put `find_chunk` at 6.69%, while pointer ownership checks consumed another 3.03%.

The allocator first added a dedicated 1032-byte arena class for requests just above 1KiB. One refill obtains a page containing 62 blocks while keeping the redis-uya request below 64KiB; blocks return to the class freelist and pages remain owned until a test-only full allocator reset. A 65-allocation boundary test covers two refills, payload endpoints, cache accounting, reuse and page reset. The matching 20,000-request `SET 1KiB` profile reaches 11621 req/s, `find_chunk` falls to 2.50%, and `owns_ptr` falls below the 0.5% reporting threshold with no lost samples.

The formal matrix reports 52896KiB RSS, or 1.85x Redis, versus 46240KiB and 1.62x in the event-time baseline. This is an explicit high-water retention tradeoff: arena pages are not individually unmapped. A separate fresh-process 5000-request `SET 1KiB` run measured 24596KiB RSS with 19 cached slab blocks after completion, so the arena is not accumulating one mostly empty page per value; long-run and mixed-size RSS remain part of the superiority work rather than being inferred from the CPU profile alone.

The follow-up profile still showed `server_runtime_info` at 0.61%. Every command constructed a broad `CommandRuntimeInfo` value and copied the complete `ServerConfig`, even though most configuration is stable between requests. The dynamic fields are comparatively small and must remain current for INFO, replication, maxmemory and background-task semantics.

`RedisServer` now owns one persistent runtime value. Request dispatch refreshes only dynamic counters, offsets, backlog state, excluded memory, background flags, last-save time and the current topology pointer; the connection layer continues to set protocol and no-touch fields. Stable configuration is synchronized at server initialization, the startup `requirepass` setter, successful `CONFIG SET`, and replica/master transitions. Full TCP smoke caught the initially missed startup password mutation, which is now encapsulated by `server_set_requirepass()`. The matched 20,000-request `SET 1KiB` profile rises from 11621 to 12853 req/s, and `server_runtime_info` falls below the 0.5% reporting threshold with no lost samples.

Matched hit-only GET profiles then showed `server_run_pending_aof_rewrite_at` at 2.15% for 16B values and 2.62% for 1KiB values even though no rewrite was requested. Release disassembly explained the disproportionate cost: entering the Uya-generated slow-path function probed a `0x502f8`-byte stack frame, and 96.45% of the function's annotated 1KiB samples landed in that stack-probe loop before the idle-state return.

The event loop now tests `aof_rewrite_requested || aof_rewrite_in_progress` before entering the large rewrite state machine. Active `BGREWRITEAOF` start, child polling, buffered-delta append, rename and writer replacement semantics are unchanged. On the same 40,000-key dataset, 60,000-request profiles reduce sampled server cycles from 4.662B to 4.431B for `GET 16B` and from 4.922B to 4.646B for `GET 1KiB`; the latter rises from 13447 to 13959 req/s, while the former records 14560 versus 14421 req/s under host scheduling jitter. The rewrite symbol falls below the 0.4% report threshold in both profiles with no lost samples. Unit, full integration, redis-cli, AOF rewrite and crash-matrix tests all pass.

The remaining reply path still carried full configuration state through ordinary commands. Release layout inspection showed `CommandReply` at 1176 bytes, while `command_executor_reply` and `connection_make_reply` each reserved a `0x4a8`-byte frame and initialized or copied 147 machine words even though only successful `CONFIG SET` needs a configuration candidate. The matched GET profiles reported `connection_make_reply` at 0.93%/1.12% for 16B/1KiB, with `command_executor_reply` also visible on the 16B path.

`CommandReply` and `ConnectionProcessResult` now omit `ServerConfig`. `CommandRuntimeInfo.pending_config` holds the rare candidate, and the connection commits it only after reply encoding succeeds. This keeps an undersized output buffer from applying a silent configuration change and preserves immediate visibility to a later `CONFIG GET` in the same pipeline. Server handling commits the complete configuration before applying a requested replica transition, so unrelated parameters in a multi-pair `CONFIG SET` are not overwritten by role synchronization. The generated `CommandReply` is now 192 bytes and `command_executor_reply` uses a `0xd8`-byte frame. On the same dataset, the 16B profile drops from 4.431B to 4.280B cycles (-3.4%) and leaves only `connection_make_reply` at 0.46%; the 1KiB profile records 4.694B versus 4.646B cycles under run-to-run jitter, with all three targeted reply helpers below 0.4% and no lost samples.

The amortized backlog design still allocated a new SDS at every physical compaction. Once a 1MiB backlog accumulated another 1MiB of discarded prefix, `sds_range` allocated and copied the live window, freed the expanded buffer, and later forced another growth back to the high-water capacity. This removed the per-command 1MiB copy but retained allocator churn and two live-window copies per physical cycle.

SDS now supports an overlap-safe in-place prefix discard that preserves allocation capacity. Backlog compaction moves the live window to offset zero inside the existing buffer and retains that high-water capacity until reset/free; allocated bytes remain visible through `mem_not_counted_for_evict`. A long-cycle unit test crosses the 64KiB test threshold with no increase in allocator allocation count, while PSYNC, full sync, incremental sync and replication consistency remain green. In an exact parent-commit comparison using one fixed key and 100,000 `SET 1KiB` requests, throughput rises from 12924 to 14218 req/s (+10.0%), sampled server cycles fall from 9.446B to 8.233B (-12.8%), `find_chunk` falls from 8.44% to 0.10%, and backlog trim falls from 0.26% to 0.15%, with no lost samples.

The remaining common parser path still allocated one `RespValue` array for every command and freed it after dispatch, even though bulk-string payloads already borrowed the connection input buffer. A unit-level `PING` allocation counter confirmed exactly one parser allocator call per request.

`RespParseResult` now records whether its element descriptors are owned. Flat command arrays with at most three Bulk/Simple String elements parse directly into connection-stack `RespValue` slots; larger argc, nested values, integer elements and other complex RESP forms fall back to the existing protocol-specific parser. Protocol and connection tests verify borrowed data, zero parser allocations, capacity fallback and unified cleanup, while full integration and redis-cli remain green. In a fixed-CPU 200,000-request `PING` comparison against parent commit `951879b`, throughput rises from 11304.7 to 11652.0 req/s (+3.1%), server cycles fall from 14.064B to 13.585B (-3.4%), instructions fall 2.3% and branches fall 2.4%.

The follow-up small-read profile showed that command-level ACL denial still scanned the full fixed deny table on every request, including the default `+@all` state with no `-command` rule. Category denial already had an active-rule count, but command denial did not, so the empty default path retained avoidable branches and name checks.

Default and named ACL users now maintain active denied-command counts alongside the existing category counts. Successful new `-command` rules increment the count, `+command` removal decrements it, and `resetcommands`, user reset and deletion clear it; duplicate adds and missing removals leave the count unchanged. Command authorization skips the fixed table when the corresponding count is zero. Unit tests cover default and named-user add/remove/reset transitions, and full integration plus redis-cli remain green. In a fixed-CPU 200,000-request `PING` comparison against parent commit `2bfb50d`, throughput rises from 11271.3 to 11543.5 req/s (+2.4%), server cycles fall from 14.093B to 13.902B (-1.35%), instructions fall 1.46% and branches fall 2.38%.

The sustained 20,000-request matrix then exposed a size-dependent allocator gap. `SET 16B` fell to 13954 req/s with 263us p99 while `SET 1KiB` remained healthy because only the 1032-byte class used batched pages. New keys, short values and dictionary entries hit the 16B through 1024B classes; once their freelists were empty, each allocation entered libc independently, so the long run accumulated allocator lookup and page-fault tail cost.

All eight classes from 16B through 1032B now refill from dynamically sized pages targeting 64KiB. The block count is derived from the class stride, so small classes receive many blocks and the 1032B class retains 62. Arena pages are process high-water storage and individual frees return to the matching freelist. Logical statistics reset no longer frees those pages because object/list pools may retain payload pointers; allocator-only tests use a separate full reset after external caches are known empty. In a matched parent/current 20K matrix, `SET 16B` rises from 14703 to 19558 req/s (+33.0%), p99 falls from 238us to 106us (-55.5%), and process RSS falls from 144452KiB to 119784KiB (-17.1%). All five regression guards pass, and redis-uya reaches 1.08x/1.29x/1.00x/1.34x/1.09x same-run Redis throughput for PING, SET 16B, GET 16B, SET 1KiB and GET 1KiB.

The shared request gate still evaluated ACL command, key and channel permissions independently for every ordinary command. In the common default-user state with no denied command or category, `allkeys` and `allchannels` enabled, none of those checks can reject the request, but the path repeatedly reconstructed the current username and entered multiple ACL helpers.

The connection layer now recognizes an unrestricted ACL user from the active deny counts and key/channel booleans. The main command path resolves the username once and skips the three detailed permission checks when the user is unrestricted; any command, category, key or channel restriction keeps the original detailed checks and error replies. A regression test restricts default-user channels, verifies denied `PUBLISH`, and verifies that non-channel `PING` remains allowed. Complete unit tests, all 33 integration tests and redis-cli smoke pass.

Two matched 50,000-request parent/current rounds show mean absolute throughput changes of -1.4% for PING, +6.7% for SET 16B, +4.0% for GET 16B, +6.1% for SET 1KiB and +4.0% for GET 1KiB. The same-run Redis-normalized ratios change by +0.3%, +20.3%, +8.0%, +15.3% and +9.2%; mean p99 is stable for SET 16B and improves for both GET cases and SET 1KiB. The immutable 50K release report passes all absolute throughput and p99 guards and records Redis ratios of 0.98x/1.30x/1.00x/1.25x/1.07x. The current formal 50K report records 1.00x/1.23x/0.91x/1.28x/0.98x, so SET is ahead while GET still requires further optimization.

A follow-up fixed-CPU `PING` profile showed that the common implicit default-user transaction still called `connection_current_username`, compared the resulting slice with `default`, and then selected the same default ACL state. The implicit state is already represented by a null transaction or `username_len == 0`, so those slice construction and keyword-comparison operations are redundant.

The request gate now checks the default ACL counters and `allkeys`/`allchannels` flags directly for an implicit default transaction. Explicitly authenticated default users and named users retain the username-based path, and any restricted default state still enters the existing detailed command, key and channel checks. Complete unit tests, all 33 integration tests and redis-cli smoke pass.

Two fixed-CPU 200,000-request `perf stat` rounds against parent commit `17f1f21` reduce mean server instructions from 931.67M to 894.04M (-4.0%), branches from 183.78M to 173.55M (-5.6%) and cycles from 2.035B to 1.972B (-3.1%); perf-instrumented throughput is effectively flat (-0.3%). A same-window 50K parent/current matrix is noisy in absolute throughput, but Redis-normalized ratios improve 8.7%/0.6%/21.9%/-1.2%/10.1% for PING, SET 16B, GET 16B, SET 1KiB and GET 1KiB. The immutable release report and the repeated current report both pass all throughput and p99 guards. The current formal ratios are 0.95x/1.26x/1.02x/1.36x/1.00x, so the change lowers CPU work without establishing broad Redis superiority.

The same profile also showed `connection_requirepass` in the ordinary command path. Authentication enablement was tested by converting the fixed 128-byte NUL-terminated `requirepass` buffer into a full slice and measuring its length, even though non-emptiness is completely determined by byte zero. AUTH and HELLO AUTH require the full slice for password comparison, but the common command gate does not.

The authentication gate now checks `runtime.config.requirepass[0]` directly. Configuration parsing, startup arguments and successful `CONFIG SET requirepass` already preserve the NUL-terminated buffer contract, so no parallel cache or synchronization point is introduced. Full password extraction and comparison remain unchanged on authentication commands. Complete unit tests, all 33 integration tests and redis-cli smoke pass, including startup-password and runtime `CONFIG SET requirepass` coverage.

Two fixed-CPU 200,000-request `PING` rounds against parent commit `eb04709` reduce mean server instructions from 6.077B to 6.035B (-0.69%), branches from 1.131B to 1.123B (-0.74%) and cycles from 13.376B to 12.877B (-3.73%); mean throughput rises from 13542.1 to 13868.8 req/s (+2.41%). The immutable and current formal reports pass all absolute throughput and p99 guards, and the current report also passes all normalized guards with Redis ratios of 0.94x/1.33x/1.05x/1.38x/1.00x.

Default latency tracking still searched the 128-entry histogram table by lower-cased command name after every non-`LATENCY` command. Repeated top-level commands therefore paid the same string-length, character and active-slot checks even after their histogram entry had been established.

| P2 | Pipeline and concurrency | Current matrix uses one connection and pipeline 1 | Add pipeline and multi-connection matrices before claiming Redis parity or superiority |

## Target Gates

Redis superiority must be claimed only after a release-build matrix shows at least 1.10x Redis throughput with p99 no worse than Redis for the selected core cases, under identical durability, client concurrency, pipeline, dataset and hardware settings. The latest formal 50K ratios are 0.94x/1.33x/1.05x/1.38x/1.00x for PING, SET 16B, GET 16B, SET 1KiB and GET 1KiB. Absolute throughput, normalized throughput and p99 regression guards pass, but PING and both GET cases remain below the strict throughput gate. Small-read dispatch, multi-run stability, pipeline/concurrency coverage and RSS remain the next measured targets.
