# redis-uya v0.9.3 performance analysis

Generated: 2026-07-18 17:32:17 +0800

## Scope

- Host: Intel Xeon E5-2698 v4, 4 visible CPUs, Linux x86_64.
- Workload: single connection, pipeline 1, AOF enabled without explicit fsync.
- Redis baseline: same host, `appendonly yes`, `appendfsync no`, `save ""`.
- redis-uya release command: `make build-release`, using Uya `-O1` and host C `-O3 -DNDEBUG -fno-builtin -fomit-frame-pointer`.
- The benchmark contract records `debug` or `release` from `build/redis-uya.build-mode`, and `make benchmark-v0.9.3-release` rebuilds before measuring.

## Confirmed Root Causes

The replication backlog previously called `sds_range()` every time its logical size exceeded the 1MiB limit. After the buffer became full, every write allocated and copied almost the complete backlog. A 1KiB `SET` therefore introduced roughly 1MiB of extra copying per request during the steady state.

The optimized backlog keeps a logical start offset, advances it in O(1) when old bytes expire, and compacts only after the discarded prefix reaches a threshold. `histlen`, first offset and PSYNC slice semantics remain unchanged.

The next CPU profile found that the default ACL path performed a linear lookup through the generated command catalog on every command even when no category deny rule existed. The shared request gate then repeated the same command, key and channel checks inside the standard executor. For `PING`, generated catalog dispatch and lookup accounted for roughly one quarter of sampled CPU time.

The optimized ACL path maintains an active denied-category count for the default and named users, skips catalog lookup when the count is zero, and performs command/key/channel authorization once in the shared request gate. Category deny semantics remain covered by unit, redis-py and redis-cli tests. A follow-up profile no longer shows command catalog functions above the 0.5% reporting threshold.

The sustained 1KiB `SET` profile then showed `find_chunk` at 88.67% of sampled CPU. Of that, 81.81% came from `resp_alloc_elements()` because every input larger than 64 bytes allocated top-level arrays for the full 64-frame batch limit, even when the buffer contained only one command. The connection path subsequently discarded that one-frame batch and parsed the command again.

The optimized RESP batch parser starts with capacity four and doubles only when additional complete top-level frames are present. Single large commands now stay in allocator slab classes, while real pipelines retain one-pass batch parsing up to the configured limit. A follow-up 20,000-request profile no longer shows `resp_alloc_elements()` above the 0.5% reporting threshold; profiled throughput rose from about 1188 to 3157 req/s.

That follow-up profile exposed a second independent allocation bug: successful standard commands always built a fully quoted MONITOR line before scanning the monitor fd table. With no monitor subscribers, 1KiB `SET` still spent about 53% of sampled CPU growing and copying a line that was immediately discarded.

The monitor registry now maintains an active subscriber count across registration, `RESET`, connection close, transaction cleanup and failed sends. Broadcast returns before allocating an SDS when the count is zero. Real cross-connection monitoring behavior remains unchanged. The next 20,000-request profile reaches 10993 req/s under `perf`, and monitor line construction no longer appears above the 0.5% threshold.

The next event-loop profile showed `server_run_blocked_clients_at()` consuming about 1.9% of samples while no blocking command was pending. The server scanned all 64 client slots on every loop iteration even though the common benchmark never enters a blocking state.

The server now counts clients only after their blocked request has been stored, decrements on successful rescheduling, `CLIENT UNBLOCK` and connection close, and skips the scan while the count is zero. Blocking list/zset wakeup, timeout and explicit-unblock tests remain green. A follow-up 20,000-request profile reaches 12278 req/s and no longer reports the blocked-client scan; the next idle full-table cost is `server_run_buffered_clients_at()` at about 2.2%.

The buffered-client pass had the same common-case problem: after a request was fully consumed, the main loop still scanned all 64 client slots to discover that every `input_len` was zero. The server now tracks clients that actually retain input bytes. Network reads add a client only on the zero-to-nonzero transition; full consumption, close, blocking reschedule and request prepending keep the count synchronized. A zero count skips the scan without changing half-packet, pipeline, pause or blocking semantics.

The matching 20,000-request `SET 1KiB` profile reaches 11751 req/s under `perf`; `server_run_buffered_clients_at()` falls below the 0.5% reporting threshold with no lost samples. The highest user-space symbols are now backlog SDS growth through `find_chunk` at 5.32%, pointer ownership checks at 3.93%, and repeated `default_config` construction at 3.25%.

`CommandReply.config_after` is meaningful only when `request_config_set` is true, but every ordinary reply previously called `default_config()` to populate that inactive field. The same unnecessary full configuration construction existed in zero-copy and batch `ConnectionProcessResult` placeholders. These inactive fields now use zero initialization; successful `CONFIG SET` still copies `runtime.config`, applies updates, sets the request flag and returns the full new configuration.

The follow-up profile reaches 11130 req/s under `perf`. `config_default_config` and its `copy_literal` helper disappear below 0.5%; `command_executor_reply` itself is 1.02%. The release matrix guard passes on the first run, with both SET cases above the per-case Redis superiority throughput threshold and lower p99.

That profile then showed `_pthread_registry_find` at 2.24% in the Future boxing allocator lookup. Uya's interface Future conversion boxes the small read/write future through `async_box_alloc_current`; redis-uya already owns a single-thread `AsyncFramePool`, but every box still queried pthread TSD to recover it.

`std.async` now exposes an explicit single-thread allocator binding. The default setter retains pthread TSD and disables the fast mode, while the server loop opts into a direct process-local allocator pointer under its existing single-thread invariant. The 20,000-request follow-up reaches 10959 req/s under `perf`; `_pthread_registry_find`, `pthread_getspecific` and `std_get_async_frame_allocator` all fall below 0.5% with no lost samples.

The server still read the millisecond clock independently for pause checks, command execution, pause deadlines and client interaction timestamps within one epoll dispatch. Those values describe the same event batch, while cron maintenance and epoll timeout calculation need explicit refresh boundaries.

`RedisServer.event_time_ms` now caches the active event-batch timestamp. The loop refreshes it for maintenance, after maintenance before deriving the epoll timeout, and after epoll returns; command execution, `CLIENT PAUSE`, accept and read interaction updates reuse the cached value. Full pause, idle-client, blocking, slow-reader and persistence integration coverage remains green. In matched 20,000-request profiles, clock-stack samples fall from 40/707 (5.66%) to 32/667 (4.80%), while `SET 1KiB` rises from 10959 to 11287 req/s. Clock work remains visible because the loop deliberately preserves independent maintenance, timeout and post-wait refresh points.

The next write profile showed that a 1KiB string value creates a 1025-byte SDS payload: 1024 data bytes plus the terminating zero byte. That payload missed the existing 1024-byte slab class, so every new value entered the underlying allocator. In the event-time baseline, backlog growth and per-value allocation put `find_chunk` at 6.69%, while pointer ownership checks consumed another 3.03%.

The allocator now has a dedicated 1032-byte arena class for requests just above 1KiB. One refill obtains a page containing 62 blocks while keeping the redis-uya request at 65480 bytes and the Uya heap mapping within 64KiB after allocator metadata; blocks return to an unbounded arena freelist and pages remain owned until the test-only allocator reset. Existing 16-byte through 1024-byte classes retain their 64-block cache limit and individual-free behavior. A 65-allocation boundary test covers two refills, payload endpoints, cache accounting, reuse and page reset. The matching 20,000-request `SET 1KiB` profile reaches 11621 req/s, `find_chunk` falls to 2.50%, and `owns_ptr` falls below the 0.5% reporting threshold with no lost samples.

The formal matrix reports 52896KiB RSS, or 1.85x Redis, versus 46240KiB and 1.62x in the event-time baseline. This is an explicit high-water retention tradeoff: arena pages are not individually unmapped. A separate fresh-process 5000-request `SET 1KiB` run measured 24596KiB RSS with 19 cached slab blocks after completion, so the arena is not accumulating one mostly empty page per value; long-run and mixed-size RSS remain part of the superiority work rather than being inferred from the CPU profile alone.

The follow-up profile still showed `server_runtime_info` at 0.61%. Every command constructed a broad `CommandRuntimeInfo` value and copied the complete `ServerConfig`, even though most configuration is stable between requests. The dynamic fields are comparatively small and must remain current for INFO, replication, maxmemory and background-task semantics.

`RedisServer` now owns one persistent runtime value. Request dispatch refreshes only dynamic counters, offsets, backlog state, excluded memory, background flags, last-save time and the current topology pointer; the connection layer continues to set protocol and no-touch fields. Stable configuration is synchronized at server initialization, the startup `requirepass` setter, successful `CONFIG SET`, and replica/master transitions. Full TCP smoke caught the initially missed startup password mutation, which is now encapsulated by `server_set_requirepass()`. The matched 20,000-request `SET 1KiB` profile rises from 11621 to 12853 req/s, and `server_runtime_info` falls below the 0.5% reporting threshold with no lost samples.

Matched hit-only GET profiles then showed `server_run_pending_aof_rewrite_at` at 2.15% for 16B values and 2.62% for 1KiB values even though no rewrite was requested. Release disassembly explained the disproportionate cost: entering the Uya-generated slow-path function probed a `0x502f8`-byte stack frame, and 96.45% of the function's annotated 1KiB samples landed in that stack-probe loop before the idle-state return.

The event loop now tests `aof_rewrite_requested || aof_rewrite_in_progress` before entering the large rewrite state machine. Active `BGREWRITEAOF` start, child polling, buffered-delta append, rename and writer replacement semantics are unchanged. On the same 40,000-key dataset, 60,000-request profiles reduce sampled server cycles from 4.662B to 4.431B for `GET 16B` and from 4.922B to 4.646B for `GET 1KiB`; the latter rises from 13447 to 13959 req/s, while the former records 14560 versus 14421 req/s under host scheduling jitter. The rewrite symbol falls below the 0.4% report threshold in both profiles with no lost samples. Unit, full integration, redis-cli, AOF rewrite and crash-matrix tests all pass.

## Target Gates

Redis superiority must be claimed only after a release-build matrix shows at least 1.10x Redis throughput with p99 no worse than Redis for the selected core cases, under identical durability, client concurrency, pipeline, dataset and hardware settings. The latest `SET 16B/1KiB` ratios are 1.25x/1.43x, while PING and both GET cases reach 1.14x/1.11x/1.02x; every current p99 is lower than Redis. The absolute and normalized regression guards pass for every case, and all five same-run throughput ratios exceed 1.0x, but `GET 1KiB` still keeps the strict 1.10x superiority gate open. Read-path ownership, pipeline/concurrency coverage and RSS remain the next measured targets.
