# redis-uya v0.9.3 performance analysis

Generated: 2026-07-17 10:23:00 +0800

## Scope

- Host: Intel Xeon E5-2698 v4, 4 visible CPUs, Linux x86_64.
- Workload: single connection, pipeline 1, AOF enabled without explicit fsync.
- Redis baseline: same host, `appendonly yes`, `appendfsync no`, `save ""`.
- redis-uya release command: `make build-release`, using Uya `-O1` and host C `-O3 -DNDEBUG -fno-builtin -fomit-frame-pointer`.
- The benchmark contract records `debug` or `release` from `build/redis-uya.build-mode`, and `make benchmark-v0.9.3-release` rebuilds before measuring.

## Confirmed Root Causes

The replication backlog previously called `sds_range()` every time its logical size exceeded the 1MiB limit. After the buffer became full, every write allocated and copied almost the complete backlog. A 1KiB `SET` therefore introduced roughly 1MiB of extra copying per request during the steady state.

The optimized backlog keeps a logical start offset, advances it in O(1) when old bytes expire, and compacts only after the discarded prefix reaches a threshold. `histlen`, first offset and PSYNC slice semantics remain unchanged.

The next CPU profile found that the default ACL path performed a linear lookup through the generated command catalog on every command even when no category deny rule existed. The shared request gate then repeated the same command, key and channel checks inside the standard executor. For `PING`, generated catalog dispatch and lookup accounted for roughly one quarter of sampled CPU time.

The optimized ACL path maintains an active denied-category count for the default and named users, skips catalog lookup when the count is zero, and performs command/key/channel authorization once in the shared request gate. Category deny semantics remain covered by unit, redis-py and redis-cli tests. A follow-up profile no longer shows command catalog functions above the 0.5% reporting threshold.

The sustained 1KiB `SET` profile then showed `find_chunk` at 88.67% of sampled CPU. Of that, 81.81% came from `resp_alloc_elements()` because every input larger than 64 bytes allocated top-level arrays for the full 64-frame batch limit, even when the buffer contained only one command. The connection path subsequently discarded that one-frame batch and parsed the command again.

The optimized RESP batch parser starts with capacity four and doubles only when additional complete top-level frames are present. Single large commands now stay in allocator slab classes, while real pipelines retain one-pass batch parsing up to the configured limit. A follow-up 20,000-request profile no longer shows `resp_alloc_elements()` above the 0.5% reporting threshold; profiled throughput rose from about 1188 to 3157 req/s.

Compared with the recorded 2026-07-11 debug baseline, `SET 1KiB` rises from 180 to 6545 req/s, or about 36.4x. Compared with the immediately preceding release result, dynamic RESP batch capacity raises it from 2811 to 6545 req/s, or 2.33x, and reduces p99 from 1329us to 703us. An independent confirmation run measured 6884 req/s and 676us p99. This remains the largest Redis-relative performance gap.

Buffering AOF append batches up to 64KiB was measured twice against the 2133 req/s formal pre-change sample. The repeated `SET 1KiB` results were 2737 and 2955 req/s, with p99 values of 1191us and 1059us. The post-AOF, pre-ACL formal report recorded 2710 req/s and 1223us p99; the RESP allocation optimization moves the current formal result to 6545 req/s and 703us p99.

## Optimization Queue

| Priority | Area | Evidence | Next action |
|----------|------|----------|-------------|
| Done | Release benchmark contract | Project targets previously built only with C `-O0 -g`, and benchmark output always reported `debug` | `build-release` and `benchmark-v0.9.3-release` now provide a reproducible release path with recorded build metadata |
| Done | AOF medium-record path | Records above 512B previously flushed the shared buffer and called `write(2)` directly for every request | Append batches up to 64KiB now share the existing buffer; larger aggregates retain ordered direct writes |
| Done | ACL authorization hot path | Empty category deny lists still triggered two linear generated-catalog lookups per standard command | Track active category rules, skip empty catalog lookup, and keep authorization in the shared request gate |
| Done | RESP batch top-level allocation | A single 1KiB command allocated arrays for 64 frames, entered libc malloc, then was discarded and reparsed | Start at four frames and grow geometrically only when a real pipeline contains more complete frames |
| P0 | Idle MONITOR path | Follow-up 1KiB `SET` profile attributes about 53% of sampled CPU to building and growing a quoted MONITOR line when no monitor client is active | Track active monitor subscribers and skip line construction entirely when the count is zero |
| P1 | Backlog physical storage | Logical trimming removes per-request 1MiB copies, but periodic compaction and allocator residency remain visible in the 5000-request sample | Move toward a fixed-size circular or segmented backlog so steady-state append never reallocates the full history |
| P1 | RESP parse ownership | Dynamic top-level capacity removes the worst over-allocation, but each request still builds and frees a parsed value tree before dispatch | Add allocation/copy counters and introduce borrowed bulk slices for the common command-array path |
| P1 | String write allocation | `SET` creates a new object and SDS value, inserts a copied key, and updates WATCH metadata | Profile object allocation, value copy, dict insert and watch-version work separately; reuse storage on overwrite where semantics allow |
| P1 | Event-loop round trip | Release `PING` improved to 0.80x Redis; perf now points to network syscalls, async frame allocation/TLS lookup and time sampling | Remove avoidable per-poll async allocation and redundant clock reads before considering event-loop redesign |
| P2 | Pipeline and concurrency | Current matrix uses one connection and pipeline 1 | Add pipeline and multi-connection matrices before claiming Redis parity or superiority |

## Target Gates

Redis superiority must be claimed only after a release-build matrix shows at least 1.10x Redis throughput with p99 no worse than Redis for the selected core cases, under identical durability, client concurrency, pipeline, dataset and hardware settings. Small `SET` now reaches that gate in the formal matrix, but `PING`, reads and especially `SET 1KiB` still miss the full target.
